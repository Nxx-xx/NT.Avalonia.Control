# PDF Viewer 官方桌面能力对齐矩阵

核对日期：2026-10-15；阅读面（P2）状态列于 2026-10-22 按[阅读版状态](pdfviewer-status.md)第二～第十批收尾记录更新。范围为 Windows / Linux 桌面，依据官方公开文档和本仓库源代码；未读取商业控件实现或程序集。本文件是剩余工作清单，**不是新功能已实现的声明**。

目标是独立实现同等能力和可验证的使用效果，不要求同名属性、模板结构或二进制 API 兼容。继续保留 `NT.AvaloniaControl.PdfViewer` 功能包、单向依赖它的 `.Themes` 包和统一 Demo / 独立 Usage。

## 基线和阶段约定

当前证据来自 [现状记录](pdfviewer-status.md)、[使用说明](pdfviewer-usage.md)、`src/NT.AvaloniaControl.PdfViewer/` 及其 Themes、测试、Demo。P1 已补公共契约、权限、调度和异步释放，以及本机 Ubuntu WSLg 原生验证 / 专属 CI；具体执行和未验边界见 [P1 验证](pdfviewer-p1-validation.md)。Ubuntu 24.04 主目标、麒麟、不同 DPI、物理输入及辅助技术仍须独立验收。

状态：**已完成**表示现有代码覆盖列出的当前能力；**部分**表示已有基础但离该行目标有缺口；**未做**表示没有相应实现。任何状态均不自动意味着 Windows / Linux 双平台通过，平台结果单独记录。

优先级：**B0** 为决定架构或发布可行性的阻断项；**B1** 为官方桌面语义对齐必须项；**B2** 为超出官方当前公开能力的增强项。编号 F01–F64 保持稳定，后续新增条目向后追加，不重排已有编号。

本表的 B0/B1/B2 是任务优先级，与主计划交付里程碑 R1/R2/R3 不同。平台必验范围采用主计划确认的 Windows x64、Ubuntu x64、麒麟 x64/ARM64；Windows ARM64 是拓展目标。CUPS 虽属官方基线之外的增强，但已纳入本产品 P8/R3 交付，不因标为 B2 就自动省略。POC01–POC06 是技术原型门槛，与主计划 G0–G9 阶段退出门槛分别编号。

2026-10-15 真实出版语料续轮形成[逐操作兼容性边界](pdfviewer-compatibility-boundaries.md)：6 份 / 314 页可读、原样保存与新增 FreeText；清理 / 删除按具体样本接受或拒绝。既有 CFF、TJ、AcroForm / XFA 保留不等于新增字体、通用部分删除或表单交互。P0 收口为可行性 / 边界，生产化与平台 / 性能终验按[阶段迁移](pdfviewer-development-plan.md#p0-当前收口范围与阶段迁移)推进；本表最终验收条件保持。

## 官方边界，不能按营销描述扩大承诺

- **Linux 服务边界**：官方没有内置 Linux 打印 / 分享。对齐目标是可替换服务、事件、能力状态和宿主示例；CUPS、portal 或桌面特定服务属于另行明确的增强，不应混入“官方原本就有”的基线。[O5]
- **选择与可访问性**：官方文字选择限当前页；本项目已有跨页选择，保留。官方正文以位图呈现，不把正文作为文字元素暴露给辅助技术；最低对齐对象是阅读器界面和表单。可访问正文另设增强验收，不能声称官方已经完整覆盖。[O3] [O6]
- **红删范围**：官方写明部分覆盖的路径 / Form XObject 不被删除，目录标题和附件也不在默认隐藏信息清理范围。我们必须明确自己的支持边界并以提取结果检查，不把“看不见”视为“已不可恢复”。[O4]
- **性能数字**：官方说明按视口解码与回收、预渲染 / 保留缓冲，以及页面图像最多单边 8192 像素 / 合计 30 MP、渲染倍率上限；没有公开首屏毫秒、FPS、峰值内存 SLA。调参值不能充当实测性能。P3-03 起解码上限已与官方同口径，仍不能据此换算成“性能优于官方”。[O7]
- **表单扩展**：公开文档没有逐项承诺 XFA、PDF JavaScript、全部自动计算 / 验证脚本或每个字段子类型。AcroForm 字段矩阵需要 PoC。XFA、脚本兼容、数字签名生成 / 完整信任链验证、OCR、任意段落编辑、移动端、浏览器均不进入本次桌面对齐承诺。[O2] [O4]
- **独立实现**：官方公开 API 是能力参考，不复制商业实现、商业资源或内部行为。现有命名和模板契约可在兼容前提下演进。

### POC04：真实红删与隐藏副本

构造文字、扫描图、重叠图、裁剪 / 旋转、嵌套 Form XObject、结构树、内嵌缩略图和已有增量修订样本。输出重新解析后，被删内容不得通过本次承诺覆盖的文字提取 / 原始对象 / 图片 / 旧修订路径取回；保留区域不发生异常丢失。对象删除会影响已有文字句柄，页面内容需要重新生成，相关缓存和选择模型也要失效。公开 API 不足时先决定可维护的补足方案。[PDFium 编辑 API](https://pdfium.googlesource.com/pdfium/+/main/public/fpdf_edit.h)

### POC05：签名保存与红删冲突

增量保存保留旧字节；真实红删需要移除这些旧字节。二者不能在同一输出上承诺“保留旧签名且已不可恢复地删除原文”。已签名文档进入红删时必须有明确的另存 / 完整重写 / 签名结果说明策略，不能静默选择增量保存。

官方提到签名文档采用增量保存；但 PDF 规范仍要求检查签名覆盖字节与 DocMDP 允许的修改类型。验收应分别记录“原签名字节保留”“签名摘要校验”“修改符合权限”的结果，不能声称任意编辑都不影响签名。签名生成与完整信任链验证不在此次对齐范围。[官方保存行为][O2] · [PDFium 签名数据 API](https://pdfium.googlesource.com/pdfium/+/main/public/fpdf_signature.h) · [PDF 规范的 DocMDP 规则](https://developer.adobe.com/document-services/docs/assets/5b15559b96303194340b99820d3a70fa/PDF_ISO_32000-2.pdf)

### POC06：可比较的性能与平台证据

建立功能样本、正常大文档、图像密集、复杂矢量、字体密集和异常文件集并锁定哈希。性能样本与故障样本分开，不能用测试特制三页文档代表产品性能。为冷启动 / 热缓存、可见页、全篇搜索、快速滚动、多实例和长时间往返阅读分别采样。

评测要同时报告图像质量、响应时间、UI 卡顿、进程峰值 / 稳态内存及取消延迟。官方控件若没有可合法运行的对比环境，则先交付本项目绝对基线和测试工具，将“达到官方性能”标为待测，不能以同用 PDFium 直接推断相当。Linux 必须以目标系统原生窗口结果验收，Headless 和 native runtime 文件存在均不足以替代。
