# PdfViewer 剩余开发完整计划

计划基线：2026-10-15。目标是在现有桌面阅读版上，完成 Avalonia 官方 PDF Viewer 的桌面功能对齐和可复验的性能对照，交付可在 Windows 与 Linux 发布的独立控件。本文是开发计划；后文所有未实施任务、性能阈值和预计投入都不是已完成的结果。

用户已确认 Linux 按默认范围规划：Ubuntu LTS x64 建立持续集成，麒麟 x64 / ARM64 纳入实机验收。Ubuntu 24.04 LTS 作为建议主基线；P0 登记精确镜像 / 补丁 / 设备的可用性，取得目标后固定实际组合，P1 原生验证、P9 终验。Windows 以 Windows 11 x64 为主基线，Windows ARM64 列拓展验证目标。

最终完成必须同时满足：

1. 冻结的官方桌面功能矩阵逐项有实现、测试、Demo 和文档证据；允许的差异明确列出并说明，不以 UI 工具按钮存在代替 PDF 功能完成。原定必需功能若缩减，必须更新基线和版本定位，不能仅添加“已知限制”就宣称完整对齐。
2. Windows 与约定 Linux 组合均完成原生运行、输入、保存、打印、部署和稳定性验收。某个目标组合缺设备时，其状态保持未验，不能计为该平台支持已完成。
3. 性能在相同硬件、文档、画质、DPI 和操作下测量，同时通过本项目绝对预算与官方相对门槛。拿不到可运行的官方参考版本时，仅能报告自身实测，不能标记性能已对齐。
4. 两个 NuGet 包、功能包自定义模板消费者、默认 Themes 消费者、统一 Demo、最小 Usage、锁文件和许可材料全部可复现。
5. 所有发布阻断问题关闭；未验项、官方已知限制和本产品增强项分别记录。

“对标”指用户可观察到的能力、行为、质量和性能，不要求复制官方内部架构、资源外观或二进制 API。以 P0 冻结的官方文档和可运行版本为验收基线，后续新增官方功能走差距变更记录，避免目标无限移动。

## 3. 范围与技术约束

- 保持 `NT.AvaloniaControl.PdfViewer` 和 `.PdfViewer.Themes` 单向依赖。平台服务先放功能包的明确边界中，默认不新增大而全的第三个包。Themes 只承担外观和资源，不拥有文档、原生句柄或编辑历史。
- 保留当前 Source / CurrentPage / Zoom 等消费方式、跨页选择、自定义模板和页面生命周期；预发行 API 调整要有迁移说明和消费者回归。当前 `PdfBookmark` 表示文档目录，新增用户书签模型不得混用。
- PDFium 原生调用继续全进程串行。性能优化采用优先级、时间片可行性验证、任务合并和公平性，不能直接多线程并发调用 PDFium。
- 依赖升级和后端替换必须有实际能力、许可、资产和性能评估。发现固定版本 API 不足时，先完成替代方案 PoC，不将能力缺口隐藏在 UI 中。
- Windows / Linux 是本次发布范围。macOS、移动端、WebAssembly、OCR、数字签名创建、完整 PDF 正文编辑不进入本次完成条件；不因这项计划自行移除现有 macOS 运行时依赖。
- 表单覆盖类型在 P0 冻结，AcroForm 是主线；XFA / PDF JavaScript 不因为“支持表单”而隐含承诺。
- 当前 Avalonia 版本的 Linux 发布路径以 X11 及 Wayland 会话下的 XWayland 为主。原生 Wayland 要作为升级后的独立试验，不能靠打包成功宣布支持。
- 不把原生资产存在、Headless 通过、Xvfb 通过、RenderTargetBitmap 图像或 WSL 运行等同于目标实机通过。

## 4. 架构演进和共同契约

在现有功能包内部逐步形成 `Documents`、`Rendering`、`Text`、`Editing`、`Annotations`、`Forms`、`Services`、`Interop`、`Controls` 边界，不先做整包重写。后续改名只在对应实现阶段进行。

| 边界 | 计划职责与约束 |
| --- | --- |
| 文档会话 / 数据源 | 文件随机访问、可寻址流、不可寻址流暂存、字节所有权；明确是否保持源文件句柄、取消和外部文件变化策略 |
| 原生工作调度 | 可见正文 / 交互优先，预取 / 搜索 / 缩略图分级；去重、取消、公平性、任务和文档租约、异步释放 |
| 页面呈现 | 视图模式、布局索引、DPI / 旋转 / crop / PDF 与 DIP 变换，停滚高清、缓存预算与逐页失效 |
| 文本服务 | 以 PDFium 字符索引为契约，避免当作 UTF-16 offset；按页结果索引、命中加速、选择区间及按需复制 |
| 编辑会话 | 单一修订号、事务化命令、稳定内部对象 ID、IsDirty、Undo/Redo、保存与渲染之间的一致性 |
| 批注 / 表单 | 结构化数据和交互层；PDF 原生外观 / 字体 / 字段写回；索引 / 句柄不能充当跨重载稳定 ID |
| 平台服务 | 可替换的打开 / 保存 / 打印 / 分享接口、能力查询及请求事件，按 OS 延迟加载，不让缺少 CUPS 使阅读器启动失败 |

必须在 P1 / P4 固定的共同规则：

1. 公共控件调用仍以 UI 线程为入口；原生工作、文件 I/O、长文本拼接和释放不长期占用 UI。绑定入口、显式异步入口和命令入口的错误传播方式分别明确。
2. 每个任务携带文档会话 ID、内容修订号和取消状态；缓存键还需包含页面、旋转、质量、缩放及渲染选项。旧文档、旧修订和已取消任务不得写入新 UI / 缓存。
3. 编辑、保存和 Undo/Redo 不并发修改同一原生文档。保存基于明确修订，完成后只清除已保存修订的 Dirty 状态；保存期间的新编辑不能被误标为已保存。
4. 关闭 / 替换文档先让旧 UI 失效，再由工作队列安全释放。未保存修改由可等待的宿主策略决定，不能静默覆盖或在锁内弹出对话框。
5. 所有能力采用宿主允许开关、文档权限、密码角色及当前状态的真值表；IsReadOnly 不等于禁止复制或禁止另存为。命令 CanExecute、工具启用状态、公开 API 必须一致。
6. 保存采用同目录临时文件、刷新、验证及平台适当的原子替换；处理文件占用、只读、磁盘满、断开挂载、取消和进程中止。输出流明确 seek / 所有权 / 失败时部分输出语义。
7. 对签名文档，区分签名字节保留与修改后签名验证结果；对真正内容删除采用完整重写，并禁止将原始敏感内容保存在输出的旧修订中。不能同时无条件承诺“任意编辑不影响签名”和“删除原内容”。
8. 日志与探针记录耗时、任务、版本和错误类别；不默认记录密码、表单值、选中文字或完整文档内容。

### P0：冻结基线，尽早验证最难的能力

- **P0-01** 保存当前源文件 / 依赖 / 原生资产清单和 SHA-256，固定官方参考文档日期、官方控件版本与其内核版本、功能对照表和既有差异。
- **P0-02** 建立初始真实出版语料与合成边界语料，记录来源 / 许可 / 哈希和逐操作预期；覆盖普通、长文档、扫描、CJK 与表单，并用合成样本补旋转、加密、签名和损坏边界。生产规模、真实客户异常文档及长期语料扩充归 P3 / P9，内置三页样例只用于冒烟。
- **P0-03** 冻结已有 Windows 环境及 Windows / Ubuntu / 麒麟目标矩阵，逐项记录精确版本、架构、显示会话、设备与官方参考版本的可用性；未取得的镜像 / 设备明确标待验。Linux 原生底座归 P1，物理输入和完整平台验收归相应功能阶段及 P9。
- **P0-04** 建立测量协议、原始数据格式、最小基准宿主和已有后端基线；把未测指标标为未测，不从缓存大小推导内存峰值或 FPS。完整 present harness、UI / 峰值 / 分位数和官方同机性能对照归 P3 / P9，不要求 P0 提前达到发布性能门槛。
- **P0-05** 完成四项小而完整的原型：PDF 写出与失败恢复；一条带 CJK / 外观流的可编辑批注；带真实焦点输入的表单页；真正内容删除与保存策略。验证固定 PDFium 版本的 ABI 和导出符号，不能只查最新头文件。
- **P0-06** 对 API 不足、签名 / 红删冲突、CJK 字体子集和表单页面生命周期给出技术选择及估工更新。必要时评估适当许可的写入组件或自行补足方案。

**G0 退出：** 源码 / 依赖 / 已有环境、官方能力与测量协议可复查；初始真实语料按操作形成接受 / 拒绝 / 未覆盖矩阵，拒绝有实测原因及不修改原会话的证据；四项原型和补足方案可复验；每项未完成产品能力已分配后续阶段与退出条件。缺失的官方运行版本及目标设备不能标为已冻结或已验，单列外部依赖。G0 不要求完成编辑 UI、Undo、全部字体 / PDF 兼容、Linux 全矩阵或发布性能；它们仍是后续阶段及最终发布门槛。保存 / 表单 / 红删缺少可行方案时，不冻结对应交付日期；P1 底座和其他阅读工作可并行开始。

### P4：保存与有界编辑历史

- **P4-01** 建立原生编辑事务、修订号、稳定对象 ID、Dirty 及有界 Undo/Redo；用户书签按官方边界不进入批注 / 表单撤销栈，完成其 PDF 持久化和回读。历史同时限制操作数与内存字节。
- **P4-02** 支持原路径保存、另存为、流与字节导出，提供请求事件和宿主服务；AutoSave 仅在可写来源有效，采用有序 / 可合并提交。
- **P4-03** 完成临时文件及原子替换、原文件占用与外部变化检测、取消 / 磁盘满 / 断网挂载 / 崩溃恢复；保存失败不得静默损坏原文档或丢失 Dirty。
  P0 已证实保存回调的异常必须覆盖原生 BOOL；临时文件需唯一命名且只清理本次拥有的文件。Windows 文件共享锁和 POSIX 打开描述符下的替换行为分别验收。
- **P4-04** 保留 / 显式处理加密、权限、签名与文档结构。对不同修改类别分别验证签名影响，禁止“使用增量保存就始终签名有效”的推断。

  将已验证的源 CID / 字素簇扩张与严格拒绝策略、邻字绝对位置、未用 ToUnicode / CID 映射清理接入选区和事务；图像采用像素单元保守删除、选中调用资源隔离，并明确未选共享实例仍可保留原图。扩展真实字体 / 编码 / TJ / 排版和图像格式前先补独立正例与拒绝反例，处理保守边界的 UI 预览及 Undo 内存预算。
- **P7-02** 明确结构树、缩略图、元数据、附件、目录和其他副本的清理范围；每类有测试样本。对官方已知边界单列，不把同功能对标等同于任意内容都已清除。
- **P7-03** 使用完整重写及旧修订清理，检查未引用对象与可恢复副本；通过独立文本提取 / 对象检查和视觉对照验证。字节搜索和黑框截图均不足以单独证明删除完成。
  P0 已提前实现受限的页绘制数据重建与整对象删除后端；全 xref / 解压流、作用域文字、共享实例及保留像素由独立工具验证。该完成项复用到 P7，不包含交互 UI、部分字符 / 图像编辑、任意 PDF 兼容或源文件 / 内存的安全擦除。
- **P7-04** 隔离敏感历史并设置单独操作 / 字节上限；明确 Undo 含原始内容、何时清理和输出中不得带出历史。保存、打印和分享使用已提交的新修订。
- **P7-05** 签名、加密、资源共享与失败回滚逐项验证。整页光栅化只能是明确选择的降级方案，不能代替保留原生内容的对齐验收。

**G7 退出：** 定义范围内的删除内容在重新打开、独立提取、对象 / 旧修订检查和外部阅读器中均不可恢复；不支持情景没有假成功，结果与边界有书面记录。

### P8：打印、分享与文件系统服务

- **P8-01** Windows 接入原生打印对话框和可取消作业，对齐矢量输出能力；Linux 交付 CUPS / IPP 适配器及宿主注入后备。统一页范围、份数、方向、纸张、适配及设备实际支持的单双面 / 颜色选项。打印质量独立于屏幕缓存，透明对象必须降为图像时记录范围和目标分辨率，不放大低清缓存冒充高质量打印。
- **P8-02** 输出包含当前已提交的批注和表单；验证虚拟打印文件与实体打印样张，分别记录作业提交与实际完成。
- **P8-03** Windows 分享服务和保存副本后备；Linux 明确宿主分享接口及文件导出路径，不能把打开文件或复制路径冒充系统分享。
- **P8-04** 验证无打印机、离线 / 认证失败、无 CUPS / portal / D-Bus、对话框取消、中文与空格路径、只读目录和网络挂载。所有子进程采用结构化参数，不拼接 shell 命令。

**G8 退出：** 两平台均有可用的文件和打印流程，具备打印环境时产生可核验输出；不具备服务时能力状态和错误准确，宿主可替换服务。

### P9：兼容、稳定性与发布

- **P9-01** 全量功能矩阵、真实文档语料、损坏 / 异常输入、Windows / Ubuntu / 麒麟、DPI / 多屏、物理输入、系统剪贴板、IME 和辅助技术复验。
- **P9-02** 全功能开启后的性能 A/B、8 小时长稳、100 次开关、2/4 viewer 争用、编辑 / 历史 / 保存的内存峰值和取消检查。
- **P9-03** 两包真实消费、四 RID 发布资产、主目标自包含离线运行，以及单文件 / trimming / Native AOT 目标的实际结果；普通发布不能代替裁剪 / AOT 验收，缺少实机的拓展 RID 不能写入“已验支持”。若原定必要发布模式无法实现，F60 保持未通过，完整对标发布不得仅靠说明限制而通过。
- **P9-04** 冻结源清单、依赖和原生 / nupkg 哈希、许可、测试 / 性能原始数据、平台矩阵、已知限制、API / 迁移文档、Demo 和最小 Usage。
- **P9-05** 回归其他控件及统一 Demo 生命周期，检查 CI 守卫对缺证据、失败、陈旧来源和不同版本结果能拒绝通过。沿用仓库版本策略，不因 PDF 发布擅自提升其他控件版本。

**G9 退出：** 第 1 节五条完成定义全部满足，发布检查清单逐条签有证据；平台和官方对照未验项不可被总测试通过数掩盖。

## 6. 性能验收摘要

以下是本项目的初始工程目标，供 P0 在固定参考硬件和逐份语料实测后冻结；不是官方公布的保证。完整定义、压力语料和测量方法见性能附件。

| 指标 | 普通文档 S1 初始目标 |
| --- | --- |
| 加载到首个可见页完整呈现 | p50 ≤ 0.6 秒，p95 ≤ 1.5 秒；新进程 / 进程内重开、OS 缓存状态分开 |
| 已缓存 / 未缓存普通页跳转 | p95 分别 ≤ 100 / 600 毫秒 |
| 滚动 | 60Hz 目标；帧间隔 p95 ≤ 20 毫秒、p99 ≤ 33.3 毫秒，组件连续 UI 工作块不超过 50 毫秒 |
| 停滚后可见页高清 | p95 ≤ 500 毫秒，画质与参考条件相同 |
| 搜索 | 首个命中 p95 ≤ 500 毫秒；固定 1000 页纯文本语料完整搜索初始预算 ≤ 10 秒，期间交互仍达标 |
| 取消 / 关闭 | 排队取消 p95 ≤ 50 毫秒；普通页原生取消 p95 ≤ 250 毫秒；关闭可见状态更新 p95 ≤ 100 毫秒 |
| 资源预算 | 建议默认正文 128 MiB、缩略图 16 MiB、文字 32 MiB，可配置；输入、原生、暂存 / 上传和 GPU 内存另报 |
| 长稳 | 8 小时、100 轮开关及多 viewer 无崩溃 / 死锁 / 持续增长；冷却回收后增量不超过 20 MiB 或初始基线 5% 中较大者 |
| 官方相对门槛 | 同机同画质下 S1 关键交互 p95 与峰值进程私有内存均不高于官方 1.25 倍，同时通过本项目绝对预算 |

普通、扫描、复杂矢量、大文档和恶劣输入分别设场景；复杂文档的原生取消安全点和处理时间单列，不承诺任意 PDF 都满足普通文档阈值。每份文档 / 场景 / 系统分开统计，不能把不同文档混成一个 p95。缺字、透明度 / 裁剪错误或降低清晰度的结果直接判质量失败，不能参与性能优胜结论。

每个场景至少 30 次用于初步 p50 / p95；发布级 p99 场景至少 100 次并记录尾延迟样本。固定源文件、产品 / 原生版本、DPI、窗口、缩放、预取、渲染设备和电源模式，保存原始数据。P0 调整初始目标时写明硬件和实测理由，后续不得为临时通过而放宽阈值。

## 8. 交付节奏、依赖与排期

按三次可验收的产品交付推进；R1/R2/R3 是本计划里程碑名称，不是已确定的 NuGet 版本号。

| 里程碑 | 内容 | 必须通过 |
| --- | --- | --- |
| R1：Windows/Linux 阅读增强版 | P0–P3；补阅读交互，完成主线 Linux、同画质性能及部署基线；用户书签写回依赖 R2 | G0–G3，主线原生运行与包消费；不能提前标全矩阵对齐 |
| R2：可编辑预览版 | P4–P6；批注、表单、保存和有界历史，保留 R1 性能守卫 | G4–G6，两平台输入 / 输出回读 |
| R3：桌面对标发布候选 | P7–P9；真正删除、平台打印分享、麒麟和全功能性能 / 稳定性 / 发布 | G7–G9，全功能矩阵与目标平台证据 |

关键依赖为：P0 → P1 → P4 → P5/P6 → P7/P8 → P9；P2/P3、平台接入、语料与测试可并行。保存和 Undo 底座要先于批注 / 表单的完整实现；红删方案在 P0 提前验证，不能等 P7 才发现内核缺口。平台验收从 P1 持续进行，不能在 P9 才第一次启动 Linux。

建议分三条工作线：文档 / 编辑内核；阅读交互 / Themes；性能 / 平台 / 验证。公共契约和共享文件由主线整合，每次合入固定源清单后跑对应检查，避免把不同来源或并行变化中的证据拼成一次通过。

根据 P0 暴露的 FreeText 字体资源、结构写入及内容清理缺口，P4 / P5 / P7 已合计增加 8–12 工程日；CJK 原生外观 fallback 反例又为 P6 增加 2–4 工程日，用于生产外观桥、布局和输入期间字体策略，P6 从 8–12 调整为 10–16。主表合计 **102–158 工程日**，单主线约 21–32 个工作周，另预留 **20%–30%** 用于复杂 PDF、字体 / 原生 API 和系统兼容性返修。这是条件预算，P5 / P6 / P7 的生产规模语料和交互校准前不冻结完整编辑交付日期。阶段迁移不重复计价或删除工作量；可并行工程量不直接等于日历耗时，设备和官方参考宿主等待另记。附件专项估工已包含在此范围内，不再次相加。

## 9. 风险与变更处理

| 风险 | 提前动作 | 处理原则 |
| --- | --- | --- |
| PDFium 公开 API 无法覆盖批注外观 / 表单 / 删除 | P0 固定版本 PoC 与能力表 | 先确定补足方案再冻结对应排期，其他阅读工作继续 |
| 保存后兼容、加密或签名行为不同 | P0 / P4 分类型语料和独立回读 | 不以本控件能重开代替通用兼容，不作无条件签名保证 |
| 画质预算和性能冲突 | P0 固定质量，P3 逐层对照 | 质量不达标的结果不参与性能通过结论 |
| 任务调度 / 释放阻塞 UI | P1 文档租约、异步释放与多 viewer 测试 | 原生串行约束不变，优先修生命周期而非增加并发 |
| Linux / 国产硬件 ABI 或字体差异 | P1 早期接入真实设备 | 记录具体组合和依赖，不借用别的平台通过结论 |
| 缺官方参考授权 / 缺 ARM64 或麒麟设备 | P0 列出前提和未验项 | 继续可独立完成的实现；对标 / 目标机 Gate 保持待验 |
| 计划期间官方 / Avalonia / PDFium 更新 | 固定版本和文档快照 | 定期记录差异，升级独立验证，不静默更换基线 |
| 撤销 / 保存快照和暂存带来内存与信息残留 | P4 以字节预算管理历史，P7 独立策略 | 输出不携带编辑历史，敏感暂存与生命周期有清理测试 |

每个工作项统一使用未开始、实施中、待验证、通过、失败 / 受阻状态，并附负责人、依赖、源清单和证据位置。“代码完成”“自动化通过”“目标实机通过”“与官方对照通过”分别记录；只有退出门槛满足才能推进里程碑状态。

## 10. 实施启动顺序
