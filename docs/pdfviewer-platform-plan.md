# PdfViewer Windows / Linux 平台开发与验收计划

计划日期：2026-10-15。本文是剩余开发总计划的平台工作包，任务使用 `PLAT01` 起的稳定编号，与主计划 `P0`—`P9` 阶段对应。本文定义后续工作和验收门槛，不代表其中的平台或能力已经实现、测试通过。

本轮按主计划收口 P0：固定已有环境、目标范围、依赖 / 设备 / 官方参考版本的可用性，以及初始真实语料和兼容边界；无法取得的镜像和设备继续明确标为待验。Ubuntu 原生底座与 CI 在 P1 接入，完整 UI / 性能在 P3 验证，后续保存 / 批注 / 表单 / 删除 / 系统服务按 P4～P8 增量验收，P9 完成目标平台最终复验。P0 不提前承担全部生产化和全平台实证，后续验收标准及用户已确认的麒麟范围保持不变。[主计划收口范围](pdfviewer-development-plan.md#p0-当前收口范围与阶段迁移) · [兼容性边界](pdfviewer-compatibility-boundaries.md)

## 目标范围与已知基线

- 主发布基线：Windows 11 x64、Ubuntu 24.04 LTS x64。P0 固定已有 Windows 构建并登记 Ubuntu 精确镜像 / 补丁 / 桌面 / 驱动 / 字体环境的可用性；P1 首次原生接入前冻结实际 Ubuntu 配置，后续每次正式验收关联对应环境哈希。
- 规划四 RID 产物：`win-x64`、`win-arm64`、`linux-x64`、`linux-arm64`。Windows ARM64 属于拓展验证目标，用户未指定为首发硬要求；Ubuntu ARM64 可用于 Linux ARM64 工程验证，麒麟 ARM64 仍需相应目标机验收。ARM64 必须取得原生设备运行证据；交叉发布成功和 x64 仿真成功不能代替原生验收。
- 用户已确认先按默认范围规划：Ubuntu LTS x64 建立 CI，麒麟 x64/ARM64 纳入实机验收计划。这些是计划目标，尚未验收通过；麒麟精确发行版、版本、Patch、桌面和软件源在 P0 记录为待落实项，取得镜像 / 设备后于 P1 起接入并冻结，P9 完整验收。当前没有麒麟实机通过证据。
- Ubuntu 22.04/26.04 LTS 是扩展兼容候选，按需求和设备增加；不将所有版本和所有架构的组合默认设为首版发布阻塞。UOS 仅在用户确定具体版本后加入矩阵。
- 当前 Avalonia 12.0.3 的正式 Linux 路径为 X11；Wayland 桌面通过 XWayland 运行。原生 Wayland 需要升级 Avalonia 并单独验证，不在当前版本预先承诺。官方文档将原生 Wayland 描述为 12.1.0 起的可选后端，仍有功能差异。[Avalonia Linux 集成](https://docs.avaloniaui.net/docs/platform-specific-guides/linux)
- 不扩大到 macOS、移动端、浏览器、嵌入式 framebuffer、LoongArch 或 MIPS。存在原生资产不等于该平台已通过验收；没有所需架构的 PDFium 资产时，必须另立移植与构建工作包。

仓库当前锁定 `.NET SDK 10.0.401`、`net10.0`、Avalonia `12.0.3` 和 PDFium 原生包 `155.0.8044`。功能包和 Themes 包已经分离，现有 Core/Headless 37 项、Windows x64 原生探针 21 项和独立 NuGet 消费者结果见 [桌面阅读版状态](pdfviewer-status.md)。本计划不重新解释这些历史结果。

2026-10-15 P0 已冻结当前 Windows x64 构建 `10.0.26200`、12 RID 原生二进制和 8 个 matching header 的哈希，并在当前主机完成四项 native 后端原型与独立 PDF 校验。Ubuntu 24.04 x64、麒麟 x64 / ARM64 的目标范围已登记，精确镜像 / 桌面 / 设备仍待落实，本轮没有增加 Linux、物理输入或原生 ARM64 通过证据；见 [P0 记录](pdfviewer-p0-validation.md)。

P0 FreeText 续轮的生产写入层使用跨平台 PDFsharp Core `[6.2.4]`、显式字体字节及 PDFium，不使用 GDI/WPF 或 Python 运行时；Pkcs 直接覆盖为 10.0.13。该轮实际运行仅 Windows x64。其 Core / Headless 合计 53 项、独立 NuGet 消费者 65 项是历史结果；Linux 字体和原子替换语义继续保留独立验收。

现有 `--pdf-smoke` 报告显式记录 `PhysicalInputVerified=false`、`ClipboardVerified=false`、`OtherDesktopPlatformsVerified=false`，图片是 Avalonia `RenderTargetBitmap`，不是系统桌面截图。P1 新增 `.github/workflows/pdfviewer-native.yml`，在 Windows / Ubuntu 24.04 分别运行独立 native host、Core / Headless 和双包新缓存消费者，并保留失败证据。工作流定义与实际 GitHub 作业通过分开记录；四 RID 发布、正式性能及离线验证仍待完成。

2026-10-16 P1 实施增加本机 Ubuntu 26.04 WSL2 / WSLg X11 的实际后端和原生窗口证据，环境及任务专属依赖见[Linux 验证说明](pdfviewer-linux-native.md)与[P1 记录](pdfviewer-p1-validation.md)。它不是 Ubuntu 24.04 CI 或目标实体桌面通过。ELF / ldd 审计覆盖实际加载的 PDFium、SkiaSharp 和 HarfBuzzSharp；各库符号下限不能合并推断整个产品最低发行版，缺失 ICU / 字体等运行前提必须另记。

## 平台矩阵与证据等级

| 组合 | 计划地位 | 验收要求 |
| --- | --- | --- |
| Windows 11 x64 / Win32 | 首版主基线 | 完整目标功能、性能、系统输入、DPI、保存、打印、无障碍和离线发布 |
| Windows 11 原生 ARM64 / Win32 | 拓展验证目标，非默认首发硬要求 | 原生 ARM64 进程和 PDFium，完整功能、性能；x64 仿真另记 |
| Ubuntu 24.04 LTS x64 / X11 | 首版 Linux 主基线 | 完整目标功能、性能、字体、IME、剪贴板、保存、CUPS 和离线发布 |
| Ubuntu 24.04 LTS ARM64 / X11 | Linux ARM64 工程验证目标，待硬件 | 原生 Linux ARM64 构建/运行；不能替代麒麟 ARM64 验收 |
| Ubuntu 24.04 LTS / GNOME Wayland + XWayland | 主基线的第二会话路径 | 打开/保存、焦点、DPI、选区、弹窗、IME、剪贴板及打印能力检测 |
| 麒麟，精确版本/补丁待冻结，x64 与 ARM64 | 已纳入计划的实机验收目标 | 对两个架构的指定镜像、CPU、桌面及驱动完成单独验收，不能引用 Ubuntu 结果代替 |
| Ubuntu 22.04/26.04 LTS、UOS | 按需扩展 | 单独冻结需求，先检查依赖和部署，再决定完整矩阵 |
| 原生 Wayland | 依赖升级试验 | 在批准升级的 Avalonia 版本上，按实际 GNOME/KDE 桌面单列验证 |

自动测试分四层记录：`Core/Headless` 证明模型和注入交互；`native smoke` 证明实际平台进程、窗口和运行时；`physical desktop` 证明系统输入与外部应用集成；`fixed hardware performance` 证明冻结设备上的性能。Xvfb、WSLg、虚拟机、软件渲染和真实 GPU 的结果分别归档，不能互相替代。跨架构模拟器不用于 ARM64 发布认证。

## P0：固定目标范围、已有环境和待验前提

### PLAT01 — 登记目标平台、依赖和可用性

- 对已有环境记录操作系统精确版本/构建/Patch、CPU 架构、.NET、Avalonia、PDFium、显示协议、桌面/合成器、GPU/驱动、字体包、输入法和打印服务版本；未取得的目标环境显式记录缺失项、设备入口和后续阶段。
- 将“主基线”“麒麟实机验收目标”“拓展验证目标”“可选候选”“本版不支持”写入矩阵；Windows ARM64 不默认设为首发硬门槛，Windows 10、其他 Ubuntu 版本和 UOS 不自动获得发布承诺。
- P0 登记 `.NET + Avalonia + PDFium + Skia + HarfBuzz` 的锁定版本和已知依赖约束，P1 在实际目标镜像校验有效系统依赖交集；不能只引用其中一个组件的最低 glibc 版本推断整体兼容性。
- P0 验收：已有环境可追溯，所有目标组合具有明确的已取得 / 待取得状态；缺失镜像和设备不标通过。P1 接入及 P9 正式支持验收仍要求相应组合有可复现系统镜像或安装记录、负责人和设备入口；麒麟版本未确认时保留明确待办。`.NET 10` 当前支持列表供选择目标时核对，实际产品支持以本项目验收结果为准。[.NET 10 支持系统](https://github.com/dotnet/core/blob/main/release-notes/10.0/supported-os.md)

### PLAT02 — 记录设备、官方参考和初始语料的可用性

- 列出 Windows x64、Linux x64、麒麟 x64/ARM64 目标设备和 Windows ARM64 拓展验证设备的取得状态与接入阶段；P1 起补齐 Linux 原生底座，P3 安排性能参考硬件 / 显示器，P8 安排纸张和至少一台实际打印机，P9 完整复验。Ubuntu ARM64 如作为工程验证环境，其证据与麒麟 ARM64 分开。
- 对照官方控件时使用获得合法使用权限的同一冻结版本、同机语料、相同视口/DPI/缩放/画质和交互脚本；官方试用或授权环境不可取得时，记录该对照项尚未执行。
- P0 验收：设备矩阵能指出已有数据来源和缺失条件；初始公开 / 自制 PDF 语料记录测试权限、再分发条件和文件哈希，客户保密文档不混入公开测试产物。6 份 / 314 页真实出版样本构成初始兼容性语料，不代表完整平台 / 性能覆盖；合法官方运行版本、缺失设备及未执行场景保持明确待办。生产规模和异常语料在 P3 / P9 扩充，完整平台实证按后续任务验收。

## P1：Windows / Linux 原生底座与 CI

### PLAT03 — 四 RID 原生资产、ABI 与 Linux 依赖

- 检查四 RID 发布目录实际携带的 PDFium、Skia、HarfBuzz 及依赖架构；比对 NuGet 所选 RID、原生哈希和已提交许可 manifest。
- Linux 用 `readelf` / `objdump` / `ldd` 记录实际需要的 `GLIBC`、`GLIBCXX`、`CXXABI` 及缺失共享库。固定最低目标镜像；glibc 和 musl 分开处理，首版以冻结的 glibc 系统为准。
- 将字体、fontconfig、X11、ICU、C++ 运行时等依赖分为必需项与按功能启用项。不得照抄与当前 .NET 版本不匹配的旧安装列表。
- 验收：四 RID 资产可追溯；主基线干净系统无缺库；待设备 RID 只记发布成功，不能记平台运行通过。

### PLAT04 — 原生加载、生命周期和可诊断失败

- 覆盖原生库缺失、架构不符、传递依赖缺失、无图形会话、GPU 初始化失败、受限工作目录等情形；给出清晰错误和环境诊断信息。
- 审查 P/Invoke ABI、字符串编码、回调生命周期、句柄与调用约定；保存、表单、打印等新接口均需进入审查范围。
- 继续遵守 PDFium 原生调用全进程序列化约束，覆盖应用中多个文档/多个控件实例同时运行及关闭竞态。
- 验收：失败可识别且不会崩溃、挂死或遗留后台任务；错误信息不输出密码、PDF 正文或不必要的个人路径。

### PLAT05 — 平台 CI 与原生冒烟

- 新增 `.github/workflows/pdfviewer-native.yml`，保留当前 `Verify.ps1` 快速合同回归，增加 Windows x64、Linux x64 原生窗口冒烟及报告归档。
- Linux CI 可用 Xvfb 验证 X11 基础能力；设置 D-Bus/portal 等集成环境时，报告实际可用服务。没有服务的环境不得将相关检查跳过后算成全通过。
- ARM64 使用原生 runner 或自托管机运行；只有交叉发布时，报告明确标记 `ExecutionVerified=false`。
- 固定或记录 runner 镜像，避免只写 `latest` 导致性能或兼容结果失去环境依据。
- 验收：Windows/Linux native 作业独立给出退出码、检查总数、失败/跳过项和证据路径；测试超时会失败并保存日志。

### PLAT06 — 平台探针、监督与来源清单

- 新增 `scripts/Test-PdfViewerNative.ps1`，串联发布、原生进程监督、输出捕获、超时和产物校验。只管理本次启动并持有身份的进程。
- 新增 `scripts/Test-PdfViewerNativeDependencies.sh`，补充现有 `collect-platform.sh`：系统/架构、原生加载依赖、实际显示后端、渲染路径、字体、输入法、D-Bus/portal/CUPS 能力。保留现有采集不包含主机名、用户名、序列号或网络配置的约定。
- 原生报告增加程序集/原生库/语料哈希、构建与执行平台、实际进程架构、检查类型和捕获类型。
- 验收：来源不明、报告过期、运行超时、结果缺失和产品哈希不匹配均不能形成通过结论。

## P2：阅读、输入、本地化与桌面集成

### PLAT07 — 打开/保存选择器与本地化

- 通过 Avalonia `StorageProvider` 和宿主可替换服务集成文件选择器；在 Windows、Linux portal 可用/不可用及受限会话分别验证。
- 覆盖取消、中文/空格/Unicode 路径、大小写敏感、网络挂载、可移动介质、只读目录、文件占用、路径失效和受控权限拒绝。
- 不假定 portal 返回资源始终可按普通本地永久路径使用；按实际文件/流及授权生命周期处理。[XDG FileChooser 接口](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.FileChooser.html)
- 工具栏、状态、错误、快捷键提示和对话框文本进入资源；英文/简体中文、长文本和不同数字格式下验收。
- 验收：打开错误能恢复操作；用户取消不显示错误；在无 portal 时按已验证的宿主回退路径运行或给出明确能力状态。

### PLAT08 — 系统剪贴板、拖放与外部应用

- Windows 与 Linux 实际桌面上，向文本编辑器/浏览器等外部应用复制并读回中文、多页、emoji、组合字符和 RTL 文本；按功能承诺验证文件拖放。
- Linux 明确普通剪贴板与 X11 主选择区的行为，覆盖控件失焦、窗口切换、文档关闭和剪贴板所有者生命周期。
- 自动化使用独立用户会话或具备完整恢复能力的夹具，避免破坏用户原有非文本剪贴板内容；保存无法安全恢复时记录未执行。
- 验收：系统剪贴板读回内容与逻辑选区一致，跨应用交互有原生证据，Headless 内存剪贴板结果单列。

### PLAT09 — 物理键鼠、触摸板及焦点

- 验证滚轮、高精度触摸板、PageUp/PageDown、快捷键、Tab 顺序、上下文菜单、跨页拖选、自动滚动、窗口最小化/恢复和跨应用焦点切换。
- 系统输入焦点与控件快捷键冲突要在搜索框、密码框及后续编辑器分别验证；输入框保留自身编辑操作。
- 触摸/笔输入在主计划纳入时补真实设备，不以鼠标注入结果替代触摸或笔行为。
- 验收：每种承诺设备有实际输入记录；隐藏/卸载/模板替换不会遗留捕获、拖选或持续渲染。

### PLAT10 — 搜索/密码输入与字体三层验收

- 使用真实微软拼音、IBus、Fcitx5 验证预编辑、候选框、提交/取消、焦点切换、滚动、窗口移动和 DPI 改变。
- 分别检查 PDF 内嵌字体渲染、未嵌入字体替换及控件 UI 字体回退；记录字体包、许可与版本。
- 使用 CJK、emoji、组合字符、RTL、多栏和竖排语料，分别检查显示、搜索、选择和复制；字体属性值不算实际字形回退证据。
- 验收：中文程序赋值与真实 IME 分开记录；不为使测试通过而默默联网下载字体。

## P3：性能、多 DPI 与渲染路径

### PLAT11 — 多 DPI、多显示器与坐标精度

- Windows 验证 100%/125%/150%/200%，Linux 验证 100%/150%/200%；记录桌面实际缩放方式。
- 覆盖不同 DPI 显示器之间移动、最大化/恢复、旋转、适配宽度/整页、鼠标锚点和 PDF 点坐标转换。
- 后续搜索框、批注/表单编辑器、弹窗、IME 候选框及命中区域均进入相同矩阵。
- 验收：选区、搜索高亮、批注和表单与 PDF 内容对齐，允许误差由主性能/质量计划统一规定；不能通过降低渲染清晰度获得对标性能。

### PLAT12 — 硬件渲染、软件回退和窗口生命周期

- Windows 与 Linux 分别记录实际使用的图形后端、GPU/驱动、刷新率、分辨率、DPI 和软件回退状态。
- 在真实 GPU、无 GPU/软件回退、远程或虚拟化环境分别验证启动、滚动、缩放、隐藏恢复、设备变化和窗口销毁。
- 不通过未经验证的后端切换宣称原生 Wayland 支持；后端升级影响全部已有控件时执行仓库级回归。
- 验收：每类环境有独立兼容结果，正式性能仅引用冻结硬件路径。

### PLAT13 — 四 RID 性能与官方同机对照

- 使用主计划统一语料、画质、交互脚本、缓存配置和指标，包含首屏、连续滚动、缩放、搜索、文本选择、并行文档、峰值/回收后内存及长时间运行。
- 记录冷启动/热缓存、文档哈希、引擎版本、视口/DPI、CPU/GPU 和实际进程架构；性能阈值与官方相对目标由主计划规定，平台工作包负责可重复采集和证据质量。
- Linux x64/ARM64、Windows x64/ARM64 分别建立基线。CI 主要执行回归守卫；物理参考机负责正式对照与发布预算。
- 验收：测量失败、主动等待、掉帧、超时、跳过和 OOM 均入报告；缺少官方运行结果时不写“已达到官方性能”。

## P4：保存、权限与文件可靠性

### PLAT14 — 原子保存、覆盖与文件系统语义

- 验证同目录临时文件、完整写入/刷新、原子替换、备份/另存为策略与失败恢复；实现需区分 Windows 和 Linux 文件占用、重命名及权限语义。
- 覆盖磁盘满、权限拒绝、只读文件/目录、目标占用、源文件被外部修改、取消、进程异常退出、网络盘/可移动介质断开。
- 更换密码/加密、签名状态、文档权限与增量/完整保存的行为由主保存计划定义；平台层负责准确报告和文件写入保障。
- 验收：失败保留原文件和可恢复状态，不把保存失败记为文档已保存；重开产物并校验功能、页数和内容，平台策略覆盖独立测试。

### PLAT15 — 安装目录只读、临时文件与离线权限

- 安装目录不写入缓存、用户设置或临时 PDF；使用明确的用户级数据/缓存目录，并验证受限目录与配额。
- 保存、打印、导出和后续脱敏的中间文件采用限定访问目录、可追踪生命周期与异常清理策略；不要求管理员权限才能阅读本地文件。
- 验证完全离线、无可写工作目录、无默认下载目录和 portal 授权资源的操作路径。
- 验收：权限错误可理解；未保存修改不会因临时目录清理而丢失；不在日志中保留密码或 PDF 正文。

## P5：批注与 CJK 一致性

### PLAT16 — 批注编辑、字体、外观流和跨平台重开

## P6：表单、IME 与无障碍

### PLAT18 — Windows / Linux 辅助技术

## P7：脱敏后的平台文件与重写验证

### PLAT19 — Redaction 重写产物与跨平台验证

- 在 Windows/Linux 交叉打开输出 PDF，检查渲染、文本提取、搜索、复制与对象层验证；缓存和预览不能重新显示被移除内容。

- 验收：Demo 能显示真实能力状态，错误/取消/不支持分开，平台失败不会假装打印/分享完成。

### PLAT21 — Windows 原生打印

- 接入 Windows 原生打印服务，支持主计划选项：打印机、页范围、份数、纸张、方向、适配/比例、单双面及是否包含批注/表单。

- 验证原始文档、未保存编辑、保存后的版本与打印快照关系；采用可追溯的一致输出策略。
- 覆盖无打印机、取消、驱动不支持选项、队列权限、离线打印机、作业失败和用户取消。
- 验收：虚拟打印队列检查输出内容和页序；实体设备检查中文、裁剪、透明度、颜色、缩放及双面。作业已提交与实际纸张输出分别记录。

### PLAT22 — Linux CUPS 可用适配器

- 在冻结的 Ubuntu/麒麟桌面上检测 CUPS/IPP 能力，枚举可用队列/选项，提交 PDF，返回作业身份，并处理查询/取消。
- 可使用 `lp` / `lpstat` / `cancel` 或受控 CUPS API；使用结构化参数列表，处理可执行程序缺失、服务未运行、无队列、认证/权限拒绝、离线和不可用选项。
- 不强制提升权限或更改系统打印配置；无 CUPS 环境维持正常阅读/保存能力，打印入口报告能力缺失。
- CUPS 接收 PDF 和常用作业选项，但可用纸张/双面等能力由队列和设备决定，适配器以实际检测为准。[CUPS 打印及选项](https://openprinting.github.io/cups/doc/options.html)
- 验收：自动测试使用虚拟/受控队列验证内容、选项、返回身份和取消；实体 Linux 打印机至少完成一次包含 CJK、表单、批注和多页范围的检查。

### PLAT23 — Portal、桌面分享与宿主后备

- Windows 分享使用实际平台可用服务；Linux 分享/打印 portal 作为按桌面能力检测的适配路径，不能仅因 D-Bus 存在就宣称 portal 接口可用。

- 无默认分享服务时通过宿主请求事件交由应用处理；外部程序或邮件工具不由控件静默发送内容。
- 验收：取消、目标应用不可用、portal 缺失、权限拒绝、临时文件失效都有明确结果；有目标设备和桌面证据的路径才进入支持矩阵。

## 依赖、工期和可交付边界

平台任务与主功能阶段并行推进：P1 尽早建立底座；P2/P3 为阅读回归提供输入/性能矩阵；P4 后才能稳定验收保存；P5/P6 分别增量接入批注/表单矩阵；P7 验证脱敏产物；P8 打印依赖正确的保存/导出快照；P9 对冻结候选版本完整复验。

按当前代码规模，平台专属工程可先按 **19—31 个工作日**预算，另留 **5—8 个工作日**完成最终矩阵与回归；它们包含打印和发布任务，与主计划相同条目不能重复相加。估算针对工程工作量，不是持续运行中的自动完成倒计时。设备初次接入、目标发行版依赖不匹配、原生引擎缺陷或驱动问题可能扩大投入，在 P0/P1 后据真实结果修订。

硬件前提包括 Linux ARM64、实体 Linux x64、麒麟目标机、多 DPI 显示器和实体打印机；Windows ARM64 为拓展验证再安排设备。缺少设备时继续完成其他工程、CI、打包与可获得设备的验收，缺口保持“未验证”。R1 可先交付 Windows x64 / Ubuntu x64 阅读增强版；用户确认纳入计划的麒麟 x64 / ARM64 是 R3 最终对标目标，缺设备时对应 Gate 保持待验，不能重新降为可选并宣布整个计划完成。仅 Windows ARM64 等明确拓展组合可不阻断默认主线发布，实际已支持范围必须如实公布。

麒麟 x64/ARM64 已纳入计划，但不能由“Linux 通用支持”推断通过。UOS、其他 Ubuntu 版本、原生 Wayland 和新的 CPU 架构仍需独立确定范围和验证。框架官方支持等级、运行时支持列表、原生资产可取得性和本项目已验收支持范围分别记录，最终承诺以后者为准。
P0 本轮清理 / 整对象删除后端使用 C# PDFsharp Core 与既有 PDFium，沿用跨平台依赖边界；实际通过证据仍仅为当前 Windows x64 后端和 Headless / 包消费。P1 先完成 Ubuntu 原生接入，P4 / P7 增量验收原子文件保存、严格清理 / 删除及拒绝行为，P9 在目标 Ubuntu / 麒麟复跑同一 corpus 与独立保留像素检查。不能从没有 GDI 或打包存在推导 Linux 已支持，平台退出门槛不变。

P0 字体续轮已在 Windows x64 验证三套完整 OFL 静态 TrueType 的自动子集、Full、NoSubsetting，以及简繁中 / 日 / 韩 / Ext-B / 复合轮廓 / Unicode 别名；pypdf、fontTools 和 Poppler 为独立验证工具，产品不引入 Python、系统字体发现或 GDI。新增 CID 原生调用沿用 Winapi 导出 ABI 和 size_t 的 nuint。Linux / 麒麟在 P1 原生加载、P5 / P6 字体与输入及 P9 发布矩阵中，使用同一 corpus 复跑相应字体、文本、像素和包消费；尚未取得对应实机结论，不能因阶段迁移记为通过。
