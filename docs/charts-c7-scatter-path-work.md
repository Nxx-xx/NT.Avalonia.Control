# C7-03 散点路径绘制次数试验

更新日期：2026-10-27。

**结论：三个候选均在严格像素检查阶段拒绝，散点积压仍未解决。** Windows 11 与 Ubuntu 26.04 / WSL2 的结果一致；没有把候选接入产品，没有改变 Render、原数据、采样、画质或性能门槛。产品仍为 B18，最新完整正式性能证据仍见[记录分配与柱形复测](charts-c7-record-allocations.md)：散点 Windows pending 161 / Linux pending 1040（各计划9000次）。这些是历史完整批次结果，本轮没有重新测量积压数。

## 本轮针对的成本

前一轮小视口准备只减少微秒级工作，没有稳定的端到端收益。本轮改为直接检验减少密集散点原生绘制次数的可行性，保留源数据的10000个点和绝对坐标。

基线直接借用已验证 B18 中 CirclePlan.GetFastShapes 的路径，每点依次绘制原 fill 和 widened outline，共20000次 DrawPath。试验仅在同色、不透明画刷、软件 BGRA8888 / Premul、单位变换的独立目标上进行；没有修改实际控件渲染器，也没有尝试绕过调用者的活动图层。

| --- | --- | ---: | ---: | --- |
| 原描边外轮廓 | 按原路径 verb/control points 提取外轮廓，省去同色内部填充，10000次调用；没有用更大的 DrawEllipse 替代 | 47676 / 3 | 47676 / 3 | 拒绝 |

这说明这三种构造并不保持当前栅格像素。几何边界相同、点之间不相交或调用次数减少，都不足以证明抗锯齿与合成结果一致。最大通道差按0..255通道值报告；门槛仍为零差异。没有测量这些失败候选的速度，也不把调用次数下降换算成性能收益。这里没有取得足以唯一归因到某个 Skia 内部分支的证据。

## Windows / Linux 验证范围

最终同一编译探针在两端实际运行，各三个候选都在首个10000点用例发现差异，因此按每候选首失败停止。每候选原计划24种组合，剩余组合没有执行、没有登记通过。测试的固定投影区域为(77.212890625,20,1100.787109375,581.0390625)，画布1200×650、半径2、描边2、填充/描边均不透明 #155CC1，边缘AA开启，矩形clip AA关闭，背景含不透明条带。这是组件拒绝试验，不是当前平台 Chart 的完整布局、232组保真或原固定负载。

独立 Python/Pillow/NumPy 审计394项通过：重新解码最终12张PNG并逐像素计算六组差异，核对编码及BGRA哈希、实际加载的各平台B18程序集和原生库、进程退出与源码。两端对应的六张图各自编码和像素均相同。另核对294个产品输入文件与上一批冻结源码及已恢复的B18文件一致，原基准驱动、协议、oracle、相关专项测试及预算文件指纹保持。

进程退出0表示探针成功报告了拒绝结果，**不表示候选画质通过**。本轮没有改产品源码，因此没有重复全量产品测试、232组产品保真或107进程正式活动，也没有新增吞吐、首次可用、内存或present资格。

## 继续核查：透明跟踪离屏目标

路径候选被拒绝后，继续验证一个保持现有 Render 调用的方向：通过可选平台适配层装饰离屏目标，在上下文创建及Push/Pop时跟踪目标所有权，以支持后续自动加速。本轮完成的是这条接管路线的可行性检查，未实现并行或位图缓存。

实际12.0.3 SDK的元数据与IL显示：RenderTargetBitmapImpl构造自己的内部FramebufferRenderTarget，CreateDrawingContext直接调用该对象，并不重新经过可装饰的平台后端工厂。普通公开IRenderTargetBitmapImpl代理能够转发CreateDrawingContext，但Skia的DrawBitmap会强制转换为内部IDrawableBitmapImpl，代理不能仅靠转发公开成员满足这一契约。

Windows / Linux 各运行一个最小用例：原生位图绘制成功、代理上下文创建成功，代理位图再交给DrawBitmap时均实际抛出System.InvalidCastException。独立审计核对输出source为8×8纯蓝，target为16×16白底加8×8蓝块，确认正常绘制成功且失败调用没有留下部分绘制；两端图片一致。这不是渲染优化接纳测试或性能测量。

这说明该普通代理不能作为透明替换直接装入产品，不代表所有自动加速方案都不可能。没有通过私有字段注入、运行时改写SDK或替换用户Render入口来绕过约束。

若继续这条路线，需要先隔离验证SDK扩展：保留原生位图对象的身份，提供可选上下文创建/后端特性入口；可靠暴露当前活动栅格目标的格式、颜色空间、origin、stride、生命周期与独占访问契约；无法证明状态时回退。仅知道根Surface，或仅记录SaveCount，不足以让原并行原型自动启用。依赖分发、版本兼容、维护成本和完整画质/净收益仍未验证。

源码TargetDecoratorProbe.cs、实际SDK方法token/IL和程序集哈希target-decorator-sdk-v1.json、双端target-decorator-v2进程/图片及target-decorator-independent-audit-v1.json均在本轮证据目录。首版缺少继承接口成员的编译失败及读取元数据时空DeclaringType处理修正均保留；修正后实际进入上述运行期拒绝，不把编译失败当作SDK运行证据。

## 剩余问题与后续范围

1. 散点固定负载与尾部波动继续开放，本轮没有可接纳的性能改动。
2. 后续候选需要保留原始逐点抗锯齿和混合计算；这三种减少DrawPath调用的具体构造已排除，不再重复试验。公开DrawingGroup仍需独立可变节点与活画刷，活动图层/位图复用限制见[上一批SDK可行性核查](charts-c7-small-native-plan.md)。
3. 普通公开目标代理已在双端运行期被拒绝；下一步如继续目标接管路线，应先隔离验证上述SDK扩展与分发/维护成本，再接回原并行候选和原协议。当前没有已经证明安全且能解决积压的替代实现，不将“尚未找到入口”写成不可能优化。
4. 官方无许可继续blocked-reference，倍率/测量为null；真实present和正式峰值内存未取得。实机、硬件GPU、物理触控、百万点命中尾延迟和原生无障碍桥接按用户决定后置。C7-03不结项。
